# Cloudflare Quick Tunnel Documentation

## Overview

This project uses a **Cloudflare Quick Tunnel** to expose the application securely over HTTPS without purchasing a custom domain or using a paid Cloudflare plan.

The Quick Tunnel provides a temporary public HTTPS hostname that forwards traffic through `cloudflared` to the local Minikube NGINX Ingress.

The architecture is:

```text
Internet
   │
   ▼
Cloudflare HTTPS
   │
   ▼
Cloudflare Quick Tunnel
   │
   ▼
cloudflared
   │
   ▼
Minikube
   │
   ▼
NGINX Ingress
   │
   ├── / → Frontend
   │
   └── /api → Backend
```

## Why Cloudflare Quick Tunnel Is Used

The project intentionally uses Cloudflare Quick Tunnel because it allows the application to be tested from an external network without requiring:

- A purchased domain
- A publicly managed DNS zone
- A paid Cloudflare subscription
- A permanent public hostname

This is appropriate for the project's development, testing, and DevSecOps demonstration environment.

## No Custom Domain

No custom domain has been purchased or configured for this implementation.

The project therefore does not use a hostname such as:

- app.example.com
- api.example.com

Instead, Cloudflare generates a temporary hostname under:

`*.trycloudflare.com`

Example:

```
https://gardens-pdf-asin-since.trycloudflare.com
```

The generated hostname is provided by Cloudflare when the Quick Tunnel starts.

## No Paid Cloudflare Plan Required

The implementation does not depend on a paid Cloudflare subscription.

The project uses Cloudflare's Quick Tunnel functionality for temporary external access.

This means the Cloudflare portion of the project can be demonstrated without purchasing:

- A domain
- Cloudflare DNS hosting for a personal domain
- A paid Cloudflare plan

## Temporary trycloudflare.com Hostname

The hostname generated by a Quick Tunnel is temporary.

For example:

```
https://gardens-pdf-asin-since.trycloudflare.com
```

The hostname should be considered valid only while the corresponding Quick Tunnel is running.

When the tunnel is stopped and a new Quick Tunnel is started, Cloudflare may generate a different hostname.

Therefore, the project must not assume that a particular trycloudflare.com hostname will remain unchanged.

## Quick Tunnel Hostname Can Change

A new Quick Tunnel can generate a different public hostname.

For example:

Previous tunnel:
```
https://gardens-pdf-asin-since.trycloudflare.com
```

New tunnel:
```
https://another-generated-name.trycloudflare.com
```

Because the hostname can change, the backend must not permanently store the generated Cloudflare hostname in Terraform or source control.

Instead, the generated hostname is injected into the backend at runtime through:

`FRONTEND_ORIGIN`

This prevents every tunnel restart from requiring a Terraform configuration change or Git commit.

## Runtime FRONTEND_ORIGIN

The backend CORS configuration uses the FRONTEND_ORIGIN environment variable.

The Terraform configuration keeps a stable default:

```
http://localhost:3000
```

When the Quick Tunnel starts, the startup script detects the generated Cloudflare hostname and updates the running Kubernetes Deployment:

```
FRONTEND_ORIGIN=https://<generated-name>.trycloudflare.com
```

The backend Deployment is then rolled out so that the new environment variable becomes available to the application.

This separates:

- Infrastructure configuration

from:

- Temporary runtime configuration

## The Quick Tunnel Is Not a Permanent Production Endpoint

The generated trycloudflare.com hostname must not be treated as a permanent production DNS endpoint.

It is intended for:

- Development
- Testing
- Demonstration
- External validation
- Temporary public access

It should not be used as the permanent hostname for a production deployment.

A production deployment would normally use a stable custom domain and appropriate Cloudflare DNS/Tunnel configuration.

## Custom DNS Is Outside the Scope of This Project

Because this project intentionally uses a free Quick Tunnel without purchasing a personal domain, DNS management for a personally owned domain is outside the scope of this implementation.

The project therefore does not configure:

- example.com
- app.example.com
- api.example.com

through Cloudflare DNS.

The public hostname is instead generated automatically by Cloudflare.

## Startup Script

The Quick Tunnel is started using the following script:

```
/home/chaos-mk/Documents/DevSecOps-projects-scripts/start-ritual-growth-tunnel.sh
```

The script is intentionally not configured to start automatically when the computer boots.

The tunnel is started manually when the environment needs to be exposed externally.

## Starting the Application Tunnel

After Minikube, Vault, and the Kubernetes infrastructure are running, execute:

```
sudo /home/chaos-mk/Documents/DevSecOps-projects-scripts/start-ritual-growth-tunnel.sh
```

The script performs the following operations:

1. Starts cloudflared.
2. Creates a Cloudflare Quick Tunnel.
3. Waits for Cloudflare to generate the public HTTPS hostname.
4. Detects the generated trycloudflare.com URL.
5. Updates the Kubernetes applicationbib Deployment.
6. Sets the runtime FRONTEND_ORIGIN.
7. Waits for the backend Deployment rollout.
8. Verifies the runtime FRONTEND_ORIGIN.
9. Prints the final public frontend URL.

Example:

```
===== STARTING CLOUDFLARE QUICK TUNNEL =====
cloudflared PID: 117203
Waiting for Quick Tunnel URL...

Cloudflare URL detected:
https://gardens-pdf-asin-since.trycloudflare.com

===== UPDATING BACKEND FRONTEND_ORIGIN =====
deployment.apps/applicationbib env updated

===== WAITING FOR BACKEND ROLLOUT =====
deployment "applicationbib" successfully rolled out

===== VERIFYING RUNTIME CONFIGURATION =====
Runtime FRONTEND_ORIGIN:
https://gardens-pdf-asin-since.trycloudflare.com

==============================================
Cloudflare Quick Tunnel is READY
Frontend URL: https://gardens-pdf-asin-since.trycloudflare.com
==============================================
```

The URL printed at the end is the URL that can be provided to an external tester.

## Important Operational Behavior

The Quick Tunnel should be started after the Kubernetes application is running.

Typical startup order:

```
1. Start Minikube
       ↓
2. Start Podman exporter
       ↓
3. Start Terraform-managed infrastructure
       ↓
4. Unseal Vault
       ↓
5. Verify Kubernetes pods
       ↓
6. Start Cloudflare Quick Tunnel
       ↓
7. Script updates FRONTEND_ORIGIN
       ↓
8. Backend rolls out
       ↓
9. Public HTTPS URL is printed
```

## Shutdown Behavior

The Quick Tunnel is not intended to run permanently.

When the development environment is shut down, the Cloudflare tunnel process can be stopped along with the local Kubernetes environment.

When the environment is started again, a new Quick Tunnel can be created using:

```
sudo /home/chaos-mk/Documents/DevSecOps-projects-scripts/start-ritual-growth-tunnel.sh
```

A new temporary hostname may be generated.

The startup script automatically updates the backend's FRONTEND_ORIGIN, so no Terraform or Git change is required for the new hostname.

## Design Decision

The project intentionally uses runtime configuration instead of committing the Quick Tunnel hostname to Terraform.

This was chosen because the Quick Tunnel hostname is temporary and can change.

The stable Terraform configuration therefore contains:

```
FRONTEND_ORIGIN=http://localhost:3000
```

while the runtime startup script injects:

```
FRONTEND_ORIGIN=https://<current-quick-tunnel>.trycloudflare.com
```

This avoids:

- Hard-coding temporary Cloudflare hostnames
- Creating Git commits after every reboot
- Running Terraform every time the tunnel hostname changes
- Coupling infrastructure code to temporary runtime state

## Project Limitation

This implementation intentionally prioritizes a free, reproducible demonstration environment over a permanent production hostname.

The following are therefore intentional limitations:

- No purchased domain
- No custom Cloudflare hostname
- No permanent DNS record
- No paid Cloudflare plan
- Quick Tunnel hostname can change
- Public URL is temporary
- Tunnel must be started manually
- Runtime FRONTEND_ORIGIN changes when the tunnel hostname changes

These limitations are accepted because the purpose of this implementation is to demonstrate secure external application access through Cloudflare while keeping the project free of domain and paid-service requirements.
